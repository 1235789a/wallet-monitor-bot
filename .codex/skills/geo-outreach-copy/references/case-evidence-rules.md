# CASE_EVIDENCE_RULES v1.0 — real evidence, not marketing artwork

## Three claim levels
- `WEBSITE_PRE_DIAGNOSIS`: sourced page observation, not AI rank test, not evidence of lost sales. Can offer a small page/answer adjustment only when the buyer decision is evidenced.
- `AI_QUERY_OBSERVED`: must store exact buyer prompt, platform/model if visible (else UNKNOWN), local/date/time and UI language if known, location constraints, full captured answer or excerpt, citation URL and competitor identity matching. One snapshot is not an exposure rate.
- `IMPLEMENTED_RESULT`: requires client permission, logged changes, same query protocol before/after, repeat controls and actual observed outcome. No guaranteed future rankings, revenue growth or paid-client labels.

## To call something an image-led mini-case
A minimum real mini-case has:
1. **Question** — the actual buyer choice or concern, not 'How is GEO?'.
2. **Evidence** — actual first-party website screenshot or independently captured AI answer, not regenerated screen, plus source URL and capture time. Crop to relevant facts; preserve enough header/context and note if translations or annotations were added.
3. **Observation** — exact text/behavior visible; if two prices differ, show tier, currency, period and eligibility before comparison.
4. **Buyer consequence** — labeled hypothesis: why uncertainty could delay procurement or exclude a supplier. Never invented numeric business loss.
5. **Smallest practical fix** — page section, content clarification or FAQ matched to buyer's query. Do not assert this improves ChatGPT rankings without test.
6. **Boundary** — `sample / not a controlled AI ranking study`; brand and private customer materials governed by permission ledger.

Image layout if asked: a clean 4:5 mobile-readable evidence card, ~75% actual unaltered screenshots, thin crop borders and short human annotations; no fake AI UI, badges, stock imagery, invented graph, design placeholders pretending to be captures, or before/after results without records. Prefer screenshots from sources, cite in supporting doc. Use real source-backed screenshots; if inaccessible, return IMAGE_EVIDENCE_BLOCKED and describe what is missing. Do not substitute generated images for proof.

## Rights and consent
- Public page screenshots for one-to-one internal review may be annotated, with links and restrained scope. Do not imply formal affiliation, endorsement or existing client relationship.
- Existing MultiHub customer conversations/test records default PRIVATE. A client agreeing to a check is not public-case permission. Do not attach another customer's identifiable case, logo, chat, exact prompt/screenshot to a new prospect.
- ANONYMIZED may still re-identify through unique domain, city, policy, screenshot: check reversibility. PUBLIC_APPROVED requires explicit scope.
- If a 'case' only describes an example plan, label `PROPOSED EXAMPLE`, not measured results.

## Package names and gates
- `INDUSTRY_NOTE`: learned buyer problem with third-party sources, no prospect-specific proof.
- `WEBSITE_FINDING`: official site observation+comparison, may support a short first-contact message after route gate; not a ChatGPT claim.
- `EVIDENCE_BITE`: one-page scoped screenshot + observed data + limitations. Send only to approved recipient and respect permission status.
- `RESULT_CASE`: actual permitted implementation and post-check, not a screenshot collage.
